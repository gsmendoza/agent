# GSM > General > Commit

## Input

- Typically uncommitted changes, but can also apply to amending commits, and other situations where commits are added or modified.

## Outcome

- Commit whose message has the following structure and format:
  - Header
    - Similar to conventional commits format.

    - <TICKET_NUMBER> <TYPE>: <Title>
      - Parts
        - TICKET_NUMBER
          - Usually JIRA ticket number.
          - Infer from branch. Exclude if cannot be inferred.

        - TYPE
          - Type of commit. Examples:
            - FEATURE
            - REFACTORING

          - Use all caps format.

          - Doesn't have to be limited to ConventionalCommits examples.

        - Title
          - Summary of what the commit does.
          - Written in imperative style.

      - Examples
        - With ticket number:
          - PROJ-123 FEATURE: Add export

        - Without ticket number:
          - FEATURE: Add export

  - Body
    - Structure
      - Include
        - In general
          - Goal
            - Explanation of reason behind commit.

            - For bugs, can be split into
              - Expected behavior
              - Actual behavior
              - Cause

      - Add a header for each section
        - Why: Makes the commit message easier to scan.
        - Example: "## Goal"

    - Writing style
      - Keep it short. Write as overview/summary.
        - Why: long commit messages are hard to comprehend.

      - Prefer bullet points over prose.

    - Format
      - Apply 72-character line limit.

## Scope

- Does not apply to commits automatically generated by Git itself, like
  - merge commits
  - revert commits
